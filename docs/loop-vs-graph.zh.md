# 循环 vs 图，工程视角

> 本文是 [`loop-vs-graph.md`](loop-vs-graph.md) 的中文翻译。以英文原稿为准；如有出入，以原文为准。

> 循环**发现**下一步做什么。
> 图**预先决定**接下来发生什么。

两者都随这个仓库发布，做同一份活，所以你可以对着读：`pikaka brief` 是循环，
`pikaka gather` 是图。下面一切都在这两个上实测。

---

## 阶梯——每一级都是你夺回控制权的一环

这些流行词按顺序到来，而顺序不是营销。每一个都是系统里你不再听天由命的一部分。

| | 你控制 | 你不再担心 |
|---|---|---|
| **prompt engineering** | 用词 | 措辞 |
| **context engineering** | 窗口里有什么 | 模型能看到什么 |
| **skills** | 流程 | 它*如何*做已知任务 |
| **loop engineering** | 调用之间发生什么 | 工具、记忆、重试 |
| **graph engineering** | 调用的形状 | 顺序和并发 |

两个诚实的提醒，免得有人抓你的错：

- **它们是叠加的；不是互相替代。** 上下文工程和循环是一起长大的，RAG 坐在两者中间。
- **每个人仍然五样都做。** 一个图不会让你的 prompt 退役。

### 大多数人跳过的那一级：skills

> **一个 skill 是用英文写下的、模型*可以*遵循的流程。
> 一个 graph 是用代码写下的、模型*不能*不遵循的同一个流程。**

这个仓库两个都有。`skills/weekly-brief/SKILL.md` 一步步描述晨间流程，循环读它并大体
遵守——但糟糕的一天它会跳一步、重排、或忘掉一个来源。图的版本跳不过一个节点。

这就给了你一条「我该不该建图？」的规则：

**先写 skill。只有它停止变动之后，才把它固化成图。**

一个 skill 十秒就能改，没有代码，没有部署。一个图你得重写。等形状定下来再付那个成本，
不要提前付。

---

## 各自在什么时候赢

**当你没法提前画出步骤时，循环赢。**

「搞定这个 PR」——读 diff、跑测试、发现需要 rebase、决定下一步。第三步取决于第二步发现
了什么。你承诺的任何图到那时都错了。这是助手做的大多数事。

**当你已经知道形状、且各部分可以重叠时，图赢。**

「每天早上给我简报」——GitHub、网页、日历、记忆。你不会*发现*那个清单；你在醒来之前
就知道了它。让模型一次一个工具调用地把这摸出来，什么都不赚，每次都花一次往返。

## 测量

同一个任务、两个引擎，对这个仓库。完整输出在 commit 历史里。

**循环**——模型决定调什么：

```
 5701ms  tool  github_read
 6078ms  tool  github_read
 6740ms  tool  list_events
 TOTAL: 15297ms
```

**图**——形状已知，所以扫描一起跑：

```
    0ms  START scan_github · scan_web · scan_calendar · scan_memory
 1889ms  done  scan_github   (1506ms)
 1890ms  done  scan_web      (1887ms)
 1890ms  done  scan_calendar    (2ms)
 1890ms  done  scan_memory      (1ms)
13170ms  done  synthesize   (11279ms)
 TOTAL: 13171ms
```

### 仔细读这个，因为标题数字是最无聊的那个

**收集：1.9s vs 6.7s——3.5 倍。** 那才是真正的效果。

**总计：13.2s vs 15.3s——14%。** 因为一次 11 秒的综合调用主导了两次运行。

> **图加速的是能并行的部分，仅此而已。**
> 如果你的工作流是一次戴了顶帽子的大模型调用，图几乎什么都不给你。

### 那个根本不是关于速度的发现

循环做了**三**次工具调用。它从没搜网页、从没搜记忆。它没有失败——它决定够了，就停了。

图抓了**四**个，因为形状说四个。

> **图不会忘。**

对一件你每天早上都跑的事，那种可靠性比那两秒值钱得多。这才是该拿出来讲的论点。

---

## 「这不就是 2023 年的确定性工作流吗？」

大体是，而且你该这么说。Airflow、Temporal 和 Step Functions 已经跑了十年条件并行 DAG。
形状是老的。

真正新的东西很窄，值得精确地说：

1. **节点是非确定性的。** 一个节点是一次模型调用；同一个输入可以产生不同输出。
2. **模型可以选边。** 路由是数据依赖的，DAG 调度器从不需要处理这个。
3. **所以你需要 Airflow 从不需要的护栏。** pikaka 的引擎给每个节点封顶访问次数、给
   总步数封顶，因为一个里面装着模型的图否则可能信心十足地永远循环。

老形状，新内容。

---

## 值得想明白的那件事

打开 pikaka 的架构图——gateway → memory → loop → tools → reply，每一轮顺序都一样。

**那已经是一个图了。** 它只是硬编码在 Python 里，而不是节点和边。

所以图引擎给你的不是形状。你早就有形状了。它给你的是把形状作为**数据而非代码**：
可检查、可从*代码本身*画出来、部分并行、无需重写函数就能重路由。

这就是诚实的卖点。它比炒作小，也比炒作有用。

## 这里是怎么建的

```
pikaka/graph/engine.py             nodes, edges, waves——整个机制
pikaka/graph/nodes.py              tool_node / llm_node / agent_node / key_router
pikaka/graph/workflows/triage.py   每条消息的前门
pikaka/graph/workflows/gather.py   晨间流程
pikaka/ops/gather.py               纯工作流与这台机器相遇的地方
```

**三个想法撑起引擎。** 状态是每个节点读取并合并进去的一个 dict——并行节点必须写不相交
的键，冲突会抛异常而不是默默丢掉一次写入。路由器是对那个状态的普通 Python 函数：模型
写它，代码读它，**没有任何模型直接决定控制流**。护栏是循环的两道护栏模式的一般化——
每节点访问封顶用于有界循环，加一个全局步数封顶。

**循环变成一个节点。** `agent_node` 跑一整轮 `run_loop`。这是人们漏掉的部分：一个图不会
替换你的循环，它*安排对循环的调用*。在 `triage` 里，`full_agent` 节点就是普通循环，
原样未动。

**波次，不是调度器。** 依赖全部满足的节点在线程池里一起跑；下一波等最慢的那个。那是
一个真实取舍——快分支在栅栏处空转——为了可读性而取。dashboard 把等待打出来，而不是
藏起来。

### 两个工作流是两份不同的活

|  | **triage** | **gather** |
|---|---|---|
| 触发 | 每条消息，自动 | 你——`make gather` |
| 频率 | 每一轮 | 每天早上一次 |
| `PIKAKA_GRAPH_WORKFLOWS` | 受它门控 | **无视它** |

值得说清楚，因为一页上的两张图看起来像你要二选一的两个选项。它们不是。

### 试试

```bash
make gather            # 图——四个来源一次抓
make brief             # 循环——同一份活，模型决定
make dashboard         # localhost:7777 → Graph → Run gather
```

Graph 标签页显示拓扑**和**一行实时卡片。图显示形状；卡片显示它正在发生，每一波的条形
共享同一条左边，因为节点共享了同一个开始。

## 安全，因为一个替你办事的晨间流程是另一种动物

`gather` **只提议，从不行动。** 不是靠指令——是靠构造：

- 它里面没有 `agent_node`、没有 `run_loop`、没有 `ToolRegistry`
- 它那一次模型调用不传 **`tools` 参数**，所以模型永远不会拿到一个它可用来发送、合并或
  创建任何东西的 schema
- 唯一的写入是 `.pikaka/outbox/` 里一个给人读的 markdown 文件

一个源码级测试在以上任何一点改变时会让 CI 失败，因为有一天有人「为了让摘要更聪明」加
一个用工具的节点时，别的什么都不会注意到。

**一个永远拿不到工具的模型，就无法使用工具。** 那是关于能力的保证，不是关于指令的——
而那是唯一值得依赖的一种保证。
