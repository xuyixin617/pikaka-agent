## 要紧的结论，全部实测

**Sean 敲定并喜欢的一句话区分：**
> 循环**发现**下一步做什么。图**预先决定**接下来发生什么。

**循环赢**，当你没法提前画出步骤——「debug 为什么我的测试失败」，每一步都取决于上一步
发现了什么。那是 pikaka 做的大多数事。

**图赢**，当你已经知道形状、步骤可以重叠。

**Sean 自己的顿悟，也是素材里最强的钩子：**
> 他打开 pikaka 现有的架构图——gateway → memory → loop → tools → reply，每一轮固定顺序
> ——说 *「那是一个图。我只是把它硬编码在 python 里，而不是节点和边。」*
>
> 所以图引擎给你的不是形状。你早就有形状了。它让形状变成**数据而非代码**：可检查、可从
> 代码本身画出、部分并行、无需重写函数就能重路由。

**他想用来开场的怀疑式框架**（他的直觉，而且对）：
> 「这不就是 2023 年的『确定性工作流』vs『让 agent 决定』吗？」大体是。Airflow/Temporal/
> Step Functions 已经做了十年条件并行 DAG。真正新的东西很窄：**(1) 节点是非确定性的，
> (2) 模型可以选边，(3) 所以你需要 Airflow 从不需要的护栏**——pikaka 的引擎给每节点
> 封顶访问次数、给总步数封顶。老形状，新内容。

**背景：** Peter Steinberger（@steipete）在 2026-07-18 发了十二个字——*「我们还在谈循环
还是已经转向图了？」*——290 万阅读。他没有定义任何东西；他戳了一下这个领域。Andrew Ng
的图课程重新点燃了它。正在浮现的共识——*图扩展循环，循环变成一个节点*——正是 pikaka 的
`full_agent` 节点做的事。

## 缺什么、能改进什么

**1. 工具测试覆盖是最大的洞。** 13 个已注册工具里有 7 个零测试引用：`browse_web`、
`create_note`、`create_reminder`、`list_events`、`read_apple_mail`、`schedule_task`、
`send_message`。`list_events` 正是那个在 Sean 真实的周四排得满满的时候告诉他日历是空的
的工具。

**2. 评估套件看不见现实。** 它测字符串生成，从不测一次调用是否成功。这就是为什么每个
Apple 工具坏了好几个星期而 CI 一直绿。旧测试字面上写着 *「covered by ... manual
verification on the dev machine」*。`evals/deterministic/test_apple_tools.py`（新）锁定了
能离线检查的部分；结构性缺口仍在。

**3. `pikaka/ops/dashboard.py` 仍是最大的文件**（拆分后约 893 行）。

**4. Apple Mail 真的不可用**——Mail.app 没法在两分钟内回答 `count of messages of inbox`
（`-1712`）。已记录，20s 内快速失败，带一条诚实的消息。不是我们的 bug。

**5. `PIKAKA_APPLE_TOOLS=1` 每个日历问题约花 13s**，就为了一行 Google 已经有的数据。
考虑在 `.env` 里关掉它，或把 Apple 折进 `list_events`，藏在仅本地日历的过滤器后面。

**6. Google Calendar 还没有随发的 OAuth 客户端**——`pikaka/tools/google_calendar.py` 里的
`CLIENT_ID`/`CLIENT_SECRET` 是空 stub。PR #42 解决这个。已做的决策：随发客户端用
**readonly scope**；写权限留在用户自己的 `.pikaka/credentials.json` 后面。

**7. `.venv` 被 worktree 清理时一个乱入的 `ln -sfn` 毁了**，不得不重建。如果任何 import
怪异，重建：`uv venv --python 3.11 && VIRTUAL_ENV=$PWD/.venv uv pip install -e '.[dev,eval,gcal]'`
